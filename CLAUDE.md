# CLAUDE.md

## Project

**medgemma-studio** — Streamlit app for analyzing medical text and images using Google MedGemma on Apple Silicon with MLX. Single-file app: `streamlit_app.py`.

## Commands

```bash
uv sync                                 # Install dependencies
uv run streamlit run streamlit_app.py   # Run the app
uv run ruff check .                      # Lint
uv run ruff format .                     # Format
uv run ty check                          # Type check
uv run pytest                            # Run tests
uv run pytest tests/test_app_ui.py -k wsi # Run one file / one name pattern
```

The hooks below already run `ruff` on every `.py` edited **via `Edit`/`Write`**, and `pytest` at the end of any turn that armed the sentinel — but **`ty` is CI-only**, so a type check is always yours to run, and a `.py` changed through `Bash` (`sed`, a heredoc, a script) matches no hook and leaves all four gates unrun, so run them by hand there, or to check early / scope a subset. When working with Python, invoke the relevant `/astral:<skill>` (`/astral:uv`, `/astral:ty`, `/astral:ruff`).

## Architecture

`main()` first renders the sidebar **app panel** (`render_sidebar` — `st.logo`, the title, a model link, this Mac's RAM and the per-run slice/patch cap `ram_aware_slice_cap` derives from it, the terms link) *before* `load_model()`, so it is up during the cold-load spinner. The panel holds **global facts only, no widgets** (pinned by `test_sidebar_is_an_app_panel_without_controls`): `st.tabs` doesn't tell the server which tab is showing, so a per-tab control in the sidebar would either show all four tabs' copies at once or need `on_change="rerun"` plus hand-rolled persistence for every hidden tab's widgets, since Streamlit drops the state of a widget not rendered on a run. `main()` then loads the model once (`@st.cache_resource load_model()` → `mlx_vlm.load()` + `load_config()` → `(model, processor, config)`; model `mlx-community/medgemma-1.5-4b-it-8bit`) and renders a research-only safety disclaimer (`DISCLAIMER_TEXT`, a persistent `st.warning`) in the **main area** — never the sidebar, which collapses (and starts collapsed on a phone) — above four `st.tabs`, each delegating to a `@st.fragment`-decorated `render_*_tab` with its own keyed widgets.

The page is `layout="wide"` (pinned by `test_page_uses_the_wide_layout`, reading source, since `AppTest` doesn't expose page config) and every tab is the same two-column **workspace** from `workspace_columns()` (`WORKSPACE_SPEC = [1, 1]`, `gap="large"`): **inputs** — caption, prompt, uploads, mode controls, Model settings, Run, then the imagery the model saw — beside **output** — preprocessing `st.status`, the live stream, the stale hint, the truncation warning, the persisted report (or `EMPTY_OUTPUT_HINT` before any run). Images go **under** Run, not above it: a portrait radiograph is taller than a laptop viewport's spare height, so above the button it pushed Run off-screen the moment a study was attached. The cost is that at ~900px of viewport height only the top of a radiograph sits beside the report (the whole image fits at ~1100px); every fix for that either moves Run below the fold or moves the controls out of the inputs column. Even halves, not 2:3 — at 2:3 the inputs column wrapped file chips and captions at 1280px while a short CXR report left the output column half empty. Below 640px Streamlit stacks the columns, inputs above output — which is **not** the old single-column order: the study preview (and, on a CT/WSI re-run, the previous result's stale imagery) sits between Run and the live stream, so at phone width a Run tap changes nothing in view until you scroll. Accepted, not overlooked: the server can't see the viewport to reorder for narrow screens, and this is a localhost desktop app. Tabs render the workspace by re-entering the column containers: the CT/WSI blocks write their result imagery under `with inputs:` *after* the `with output:` block that produced it, which is how the imagery lands under Run while the report starts at the top of its own column.

- **Ask** (`render_ask_tab`) — text-only Q&A. `DEFAULT_INSTRUCTION_TEXT`.
- **Chest X-ray** (`render_cxr_tab`) — like every other tab, `tab_settings` renders **last, directly above `Run`**, so the collapsed persona box never splits the primary controls (the localization caption says the instruction is ignored "below" for that reason; `test_cxr_localization_caption_discloses_override` pins the direction word, since the substring it used to assert survived a reorder unchanged).  single image; two-image **comparison** (both in one prompt labeled "First/Second image:", previewed under Run in an `st.columns(2)` pair nested in the inputs column, `DEFAULT_INSTRUCTION_COMPARE`, 600-token budget); or anatomy **localization** (single image only — padded to square, `LOCALIZATION_INSTRUCTION` asks for `[y0,x0,y1,x1]` boxes normalized to `[0,1000]`, then parsed → scaled → drawn → cropped back; the annotated image is the answer in this mode, so it draws in the **output** column while the plain study stays in the inputs column beside it). Comparison and localization are mutually exclusive.
- **Computed tomography** (`render_ct_tab`) — DICOM multi-file upload → `load_ct_volume` (HU) → `window_ct_slice` (false-color RGB) → `build_messages` with `"SLICE n"` labels → `run_model`. `DEFAULT_INSTRUCTION_CT`. The result renders a preview of slice 1 under Run in the inputs column, plus a collapsed **"View all N windowed slices"** gallery (`ct_thumbnails`), so a finding that names slice 7 can actually be checked against slice 7 — WSI needs no equivalent, since its `mark_patches` overlay already outlines every sampled patch. The gallery is **lazy** (`st.expander(..., on_change="rerun", key="ct_gallery")` + `if gallery.open:`): an expander body is computed and shipped even while collapsed, and `st.image` re-encodes every thumbnail to PNG, so the eager form paid that on every fragment rerun of a panel most sessions never open. `key="ct_gallery"` is what makes `.open` readable, and it doubles as the only handle a test has on the body — under `AppTest` the expander starts closed, so `test_ct_gallery_exposes_every_windowed_slice` drives `at.session_state["ct_gallery"] = True` to reach the slices.
- **Pathology (WSI)** (`render_wsi_tab`) — single slide (`.svs/.ndpi/.tif/.tiff`) + magnification `segmented_control` (5/10/20/40×) → `load_wsi_patches` (896px tissue patches) → `build_messages` with `"PATCH n"` labels → `run_model`. `DEFAULT_INSTRUCTION_WSI`. This is the **only** uploader allowed the raised `server.maxUploadSize` (2000 MB); the other three narrow back to `NON_WSI_MAX_UPLOAD_MB` — see Constraints.

CT and WSI share a 2000-token budget (2500 with thinking) and the same shape: preprocess inside an `st.status` (narrates phases, resolves `complete`/`error`) then stream generation below it in the output column; the result imagery (windowed slice + gallery; tissue overview + sample patch) then renders in the inputs column. Slice/patch counts are capped by `ram_aware_slice_cap` (multi-image inference is memory-heavy on unified memory).

**Pure helpers** (no Streamlit/model — unit-tested):
- `parse_response` — splits the `<unused94>`/`<unused95>` thinking trace from the answer
- `build_messages` — chat message list; one image placeholder per image, optional per-image label text
- `get_generation_params` — per-mode full instruction + `max_new_tokens` budget
- `pad_to_square`, `parse_boxes`, `scale_box`, `draw_boxes` — localization geometry (top-left pad; parse fenced/bare JSON boxes; scale `[0,1000]` → pixels; draw labeled boxes)
- `ct_thumbnails` — 256px copies of the windowed slices for that gallery; `Image.thumbnail` scales **in place**, so it copies first (the originals are what reach the model) and never upscales a small slice
- `normalize_hu`, `window_ct_slice` — CT windowing; `CT_WINDOWS` (wide/soft-tissue/brain → R/G/B) is the model's **trained** CT format, so it is fixed, not user-tunable
- `subsample_indices` — uniform slice/patch indices, endpoints included
- `load_ct_volume` — reads per-slice DICOMs, sorts by InstanceNumber, `seek(0)`-rewinds each upload before `dcmread`, converts to HU via `apply_rescale`
- `ram_aware_slice_cap` — `(default, max)` slice/patch counts scaled to installed RAM (`(10,20)` on 32 GiB, hard max 64); RAM detection memoized via `_cached_total_ram_gib`
- WSI: `mag_from_mpp`, `effective_magnification`, `pick_level`, `patch_grid` (non-overlapping 896px tiles, partial edges dropped), `tissue_mask` (saturation proxy `max−min(RGB)` excludes glass), `tissue_patches` (keep ≥25% tissue), `mark_patches`, `load_wsi_patches` (OpenSlide loader; `read_region` takes a **level-0** location but a target-level size; raises `ValueError` for unreadable / too-small / no-tissue slides)

**UI helpers** (touch Streamlit):
- `load_uploaded_image` — `image.load()` forces the decode so invalid data fails here, not later at `st.image`
- `run_model` — streams via `mlx_vlm.stream_generate` through `st.write_stream` (`cursor="▌"`), returns the accumulated string; passes `REPETITION_PENALTY`/`REPETITION_CONTEXT_SIZE` unless `penalize_repetition=False` (the localization path opts out — the penalty truncates the JSON box list); `temperature=0` (deterministic). The **first** chunk is pulled under an `st.spinner`, because prefill (the vision-tower encode of every slice/patch) precedes the first token and `st.write_stream` emits no element until then — on CT/WSI the `st.status` has already resolved, so nothing else is on screen. Takes an optional `finish` dict **out-parameter**, filled with `{"reason": <last chunk's finish_reason>}` — an out-param rather than a wider return type because all four call sites gate on `if raw is None`, and `stream_generate` reports `finish_reason` only on its **final** chunk (`"length"` on a token-cap stop, `"stop"` on EOS), so recording every chunk and letting the last write win is exact
- `warn_if_truncated` — renders the "Output stopped at the token limit" `st.warning` from the stored `truncated` flag. A run cut off at `max_new_tokens` renders byte-identically to one that finished, and truncation is routine here (a plain "Describe this chest X-ray" doesn't fit the 300-token budget). Called first in each tab's output column (so above the CXR mode branch), not from `show_response`: the CXR localization path draws boxes and a legend and never reaches `show_response`, and that is exactly where a clipped JSON list silently costs structures. With the imagery in the inputs column, nothing sits between the warning and the text it qualifies on any tab. `truncated` is stored in the result dict but deliberately **excluded from `sig`** — it's an outcome of the run, not an input to it, so including it would strand the very result it describes
- `render_thought` — thinking trace → expander, returns the answer
- `tab_settings` — per-tab system instruction + thinking toggle (independent session-state keys) in a collapsed "Model settings" expander
- `run_requested(clicked, prompt)` — the Run gate. The buttons are **deliberately not** `disabled=not prompt`: a disabled button dispatches no click event, and an `st.text_input` commits on blur/Enter only, so the user's first click would be spent committing the text and the app would appear dead. Upload gates stay on `disabled=` (a `file_uploader` commits eagerly). Callers **wrap the button call** rather than returning early, so the staleness render below still runs
- `cached_ct_volume` / `cached_wsi_patches` — `@st.cache_data` wrappers over the pure loaders so iterating on the prompt or persona against a fixed series/slide doesn't re-read it. `hash_funcs` keys on `UploadedFile.file_id` (what `UploadedFile.__hash__` itself uses): Streamlit's default hasher walks the whole payload *and* mixes in `tell()`, which both loaders leave at EOF — so under the default the CT key would change every Run and never hit. Kept **separate** from the pure loaders on purpose; decorating those directly would turn the two rewind guards into cache hits (see Gotchas). Both are `scope="session"`: a `file_id` is minted per upload per session, so an entry outliving its session can never be hit again and is just ~21 MB (CT, float32 HU) / ~48 MB (WSI) of decoded imaging waiting on `max_entries` eviction. Nothing else in the suite would notice if the cache silently stopped hitting (the app would merely re-read every DICOM each Run), so `test_ct_volume_cache_hits_on_a_second_run` counts `pydicom.dcmread` calls across two Runs — and counts generations too, so a button that never fired can't pass it

**Result persistence** — Each tab runs inference **only** inside its `Run` block, stores output + `is_thinking` + `truncated` + (for CT, the slice `thumbs` and `labels`, which are built inside the `Run` block and would `NameError` if the render below recomputed them) + a `sig` of the run-defining inputs (prompt, system instruction, `_file_sig`=**`file_id`**, localize/compare mode, slice/patch count, magnification) in `st.session_state["{ask,cxr,ct,wsi}_result"]`, and renders it **outside** the button gate via `fresh_result_or_hint(key, live_sig, empty_hint=not go)` — returns the stored dict when the `sig` matches, else shows an `st.info` "Inputs changed…" hint and drops it (so a stale result never mismatches the visible inputs). With no stored result it captions `EMPTY_OUTPUT_HINT` instead (a blank output half reads as a broken page), except on the rerun where Run was just clicked — so a failed run shows its error alone rather than an error followed by "click Run". `_file_sig` keys on `file_id`, **not** name + size, so it agrees with `_UPLOAD_HASH` on what "the same file" means: name + size collides on exactly the input this app sees most — per-slice DICOMs off one scanner share a name pattern (`IM_0001`) and, at a fixed protocol, a byte size — which would let `fresh_result_or_hint` serve the previous patient's result as fresh with no hint. It falls back to name + size for anything lacking a `file_id` (a plain `BytesIO` in a unit test). `thinking` and `truncated` are deliberately excluded from `sig`; the system instruction is **included** (it becomes the system message, so editing the persona must strand the old answer). The CXR sig substitutes `None` for it in localization mode, where a built-in prompt overrides the persona anyway. On a successful run each tab `st.rerun()`s, shedding the streamed raw copy for the clean persisted render.

## Claude Code hooks

`.claude/settings.json` (shared) runs the same gates automatically; guarded structurally **and** behaviorally (executes each command, asserts exit codes) by `TestHooksConfig`. All hooks under one matcher run **in parallel**, so the per-`.py`-edit cost is `max()`, not `sum()` — ~0.08s, all of it `ruff`. It used to be ~0.65s, ~99% of it a per-edit `ty check` that was **cut**: CI runs the identical `uv run ty check` at identical strictness (no `[tool.ty]` section), pytest already executes 98% of `streamlit_app.py`'s statements, and over the first 122 commits that hook's record here was **zero true positives and two false-positive suppressions** (`3768370`, and the `ty: ignore[unresolved-attribute]` still at `streamlit_app.py:838`) — structural, since `mlx_vlm` is the one dependency without `py.typed`. Don't re-add it per-edit; run `uv run ty check` by hand, or let CI do it:

- **`permissions.deny`** — `Read(.env)`, `Read(.env.local)`, `Read(.streamlit/secrets.toml)`. The **read** side, declarative: it also covers `cat`/`head`/`tail`/`sed` through `Bash` (but *not* an arbitrary subprocess that opens the file itself), which no `Edit`/`Write` hook can see. Two rules to keep in mind, both load-bearing: a `Read` deny rule **also blocks `Edit` and `Write`** on the same path (Claude Code ≥ 2.1.228), and **a deny rule carries no allowlist exceptions** — an `allow` rule cannot rescue a denied path, and neither can a `PreToolUse` hook returning allow. So the entries are **enumerated, never `Read(.env.*)`**: the wildcard would make `.env.example` uncreatable and silently turn the guard's carve-out into dead configuration. The trade is deliberate — a future `.env.production` is write-blocked by the guard but not read-blocked. Keep the **bare** forms too: they are gitignore-style and match at any depth, whereas `Read(/.env)` would narrow to the root file only.
- **PreToolUse** (`Edit`/`Write`) — blocks **writes** to `.env`/`.env.*` (except `.env.example`/`.sample`/`.template`), `.streamlit/secrets.toml`, `uv.lock`. Case-insensitive; matches relative as well as absolute paths; **fails closed** if `jq` is absent *or* the event has no parseable `file_path`. Accident-guard only (does not intercept `Bash` writes).
- **PostToolUse** (`Edit`/`Write`) — both entries share a prologue that resolves a relative `file_path` against the project root and then **ignores anything outside `$CLAUDE_PROJECT_DIR`** (a scratch `.py` elsewhere is not ours: linting it blocks on unrelated violations, and arming the sentinel bills the ~27s suite for a file no test covers). That prologue includes a `case "$f" in *..*) exit 0 ;; esac` clause, which is **not** belt-and-braces: joining a relative `../elsewhere/scratch.py` onto the project root yields a string that still *starts* with that root, so the prefix check alone fell open and ruff **rewrote the outside file in place** with this project's rules while reporting exit 0. `test_post_edit_hooks_ignore_files_outside_the_project` now sends the relative form as well as the absolute one — only the relative form ever caught it. Then, on `.py`: `ruff check --fix` + `ruff format` (silent) then a **blocking `ruff check` re-check** (exit 2 on whatever `--fix` can't repair — E501 on a long comment is the common one, and `ruff format` doesn't rescue it). A second, separate entry writes a `.claude/.tests-needed` sentinel (gitignored) on any `.py`/`.toml`/`.yml`/`.yaml`/`.md`/`LICENSE`/`.claude/settings.json` edit — it stays separate **on purpose**, since folding it into the `ruff` command would let that hook's `exit 2` short-circuit the arming and silently disarm the Stop gate. It also **fails safe**: if `jq` is missing or the event carries no `file_path`, it arms anyway (via the builtin `: >"$s"`, so an empty `PATH` can't stop it) rather than exiting quietly — it is the only thing that arms Stop, and the four Stop tests all stay green through a silent failure because each one creates the sentinel by hand.
- **Stop** — if the sentinel exists, runs `uv run pytest -q --maxfail=3 --tb=short` (~27s green, 360 tests); clears the sentinel on pass, blocks + feeds output back on fail. The flags are tuned to what survives `tail -n 40` across both failure regimes: bare `-q` names every small failure but **no** root cause on a broad breakage, `-x` names the cause but only one failure; `--maxfail=3 --tb=short` is the only setting that wins in both. Skipped on turns with no pending sentinel, though one *following an interrupted code turn* still pays the suite. A docs turn is **not** free any more: nine guard classes (`TestClaudeMd`, `TestDocsMatchSource`, `TestLicense`, `TestReadmeAssets`, `TestCiWorkflow`, the three workflow guards, `TestThemeConfig`) test `.md`/`.yml`/`LICENSE`/`.toml` and have no other local trigger, and **15 of the first 122 commits** touched one while arming nothing — including `bcbdd60`, the CLAUDE.md rewrite `TestClaudeMd` exists to catch, and `bc9ecc1`, which *added* `ci.yml`. Editing this file costs ~27s at Stop; that is the trade. Turns touching only untracked scratch files, `samples/`, or `docs/*.webp` are still free. `stop_hook_active` guards against a stop→fix loop, and because it stays true for **every** later stop in a turn, exactly one blocking run happens per user message (it resets on the next one, so a deferred failure is caught then).

**All of the above applies only to sessions started at the repo root** — Claude Code reads `.claude/settings.json` from the directory the session runs in, so `cd tests && claude` gets no deny rules and none of the four hooks. (`.claude/settings.local.json` is the exception: it is read from the git root, so it covers any subdirectory.) Personal overrides go there (gitignored).

## Continuous integration

`.github/workflows/ci.yml` runs all four gates (`ruff check` · `ruff format --check` · `ty check` · `pytest`) — a superset of the local hooks, which cover only `ruff` and `pytest` since `ty` was cut from the per-edit path — via `uv sync --locked` on a `macos-15` (arm64 — matches the MLX target so `TestMlxVlmContract` exercises the shipped backend), on push to `main` / PR / `workflow_dispatch`. Least-privilege `contents: read` token, 15-min timeout, badge in `README.md`. A version bump must be lock-synced (`uv lock`), else `uv sync --locked` fails.

Four details are load-bearing rather than boilerplate, and a test now pins each — `TestCiWorkflow` for three of them, `TestAutoReleaseWorkflow` for the second (an audit found all four removable with a green suite):

- **`cancel-in-progress` exempts `main`** (`${{ github.ref != 'refs/heads/main' }}`). Superseding a stale PR run is right; superseding a main run is not — a cancelled run reports `cancelled`, not `failure`, so the commit would land on main having never passed the gates, *and* `tag-and-release.yml` (which publishes only off a **successful** CI run) would silently skip its release.
- **`name: CI` is an API.** `tag-and-release.yml`'s `workflow_run` matches this workflow's `name` value, **not** its path — renaming it un-gates the publisher invisibly. `TestAutoReleaseWorkflow.test_gates_on_ci_by_name_not_path` reads the name out of `ci.yml` so a rename fails a test instead.
- **`uv` itself is pinned** (`version: "0.12.19"` on `setup-uv`). `uv sync --locked` errors unless `uv.lock` is exactly what the *running* uv would produce, so an unpinned uv lets an upstream release turn a green PR red with no repo change — indistinguishable from a genuinely stale lock. Bump it alongside `uv lock`.
- **`cache-dependency-glob: uv.lock` is narrower than setup-uv's default**, which also keys on `**/pyproject.toml` — under the default a ruff-rule or `[project.urls]` edit would miss the key and re-save for nothing. Expect little from the cache either way: setup-uv's `prune-cache` default runs `uv cache prune --ci`, which discards pre-built wheels, and *every* dependency here ships as a wheel — so the restore is ~2 KB and `uv sync` re-downloads all 84 packages regardless (measured across real runs: a cache hit's sync step beats a miss by ~1s, which is download variance, not cache benefit). Don't "fix" it with `prune-cache: false` — pushing ~236 MiB of wheels through the Actions cache to replace a ~4.4s parallel download is a net loss. `enable-cache` is deliberately *absent*: its `auto` default already resolves to on for a GitHub-hosted runner. `persist-credentials: false` on `checkout` keeps the token out of `.git/config`, since nothing in CI pushes and the steps after it execute ~100 third-party packages' code.

## Releases

Two workflows publish, and **the automatic one is the normal path**.

**`.github/workflows/tag-and-release.yml` (automatic).** Triggered by `workflow_run` on **CI's completion**, filtered to `branches: [main]`, not by `push: branches: [main]` — gating on CI's *conclusion* is what makes unattended publishing safe, since it buys the whole four-gate suite including the `uv sync --locked` step that goes red when a bump lands without `uv lock`. A `push:` trigger would race CI and publish in seconds. The `branches:` filter matters for a second reason: without it every *pull-request* CI run also starts a run here, dead-ended at the job `if:` — pure Actions-log noise, since the publish group sits on the **job** and a skipped job never claims it.

There are two entry paths and **both** end up CI-gated, by different means:

- **`workflow_run`** — the job `if:` requires the upstream run to be `success`, from a `push`, on `main`, **and** `head_repository.full_name == github.repository` (a fork's default branch is also called `main`, so the branch check alone is a trap).
- **`workflow_dispatch`** — the recovery lever, **ANDed with `github.ref == 'refs/heads/main'`**: as a bare disjunct it let anyone with write access publish from any branch or tag, since on a dispatch `github.sha` is the tip of the *dispatched* ref, which both `head_sha || github.sha` fallbacks resolve to. It cannot check a CI conclusion (there is no upstream run), so a **"Require a green CI run for this commit"** step re-imposes the invariant on both paths — the tested SHA needs a successful `event=push` CI run or the job fails. Without it, dispatching while main is red (precisely what the lever is for) would publish from a failing commit.

`TestAutoReleaseWorkflow` pins the job `if:` as one **whole normalised expression**, not as four substring checks: a substring guard is satisfied just as happily when the `&&`s are flipped to `||`, and says nothing about the dispatch clause. Mutation-tested — under the old substring form, both tightening *and deleting* the dispatch clause left the suite green.

The job checks out `workflow_run.head_sha` — on a `workflow_run` event `github.sha` is the **default-branch tip**, not the commit CI tested — then reads `version` from `pyproject.toml`, requires a plain `^[0-9]+\.[0-9]+\.[0-9]+$` (a `0.9.0rc1` left in place during WIP is skipped), and publishes.

The idempotency key is repository **state** — *"does a release already exist for `v$version`?"* — never a commit diff, which breaks under `checkout`'s default `fetch-depth: 1` (`HEAD^` does not resolve — `fatal: bad revision`), on force pushes, on several commits in one push when the bump is not the last one, and on job re-runs; a state check survives all four, so re-running the job is always a safe no-op. Publishing is a single `gh release create "$tag" --target "$SHA" --generate-notes`: `--target` **creates the tag and publishes in one API call**, so there is no window where the tag exists but the release doesn't (and that is why `--verify-tag`, which needs a pre-existing tag, is absent here). But `target_commitish` is documented as **"Unused if the Git tag already exists"**, so a tag left behind *without* a release would silently anchor the release at that tag's commit: the job therefore **refuses outright** if the tag exists, pointing the operator at `release.yml`. Never `--draft` — a draft is absent from the public releases API, so the README's release badge would freeze on the previous version, and its tag doesn't materialise until someone clicks Publish.

**The constraint that forces this shape:** GitHub documents that *events triggered by the default `GITHUB_TOKEN` do not create new workflow runs* (`workflow_dispatch` / `repository_dispatch` excepted). A bot-pushed tag is therefore **invisible** to `release.yml`'s `on: push: tags`, so the obvious "tag here, let `release.yml` publish" design is dead without a standing PAT or GitHub App secret. Tagging and publishing in one job is what avoids introducing one. Don't "simplify" it back.

**`.github/workflows/release.yml` (manual backstop).** Still fires on a pushed `v*` tag — the glob is deliberately loose, since a non-`X.Y.Z` tag is rejected by the version check below rather than by the trigger — or on a `workflow_dispatch` **from a tag**, the way to re-run it against a tag that already exists without deleting and re-pushing that tag (exactly where `tag-and-release.yml`'s existing-tag refusal sends the operator). It still **verifies the tag matches `pyproject.toml`'s `version`** (a `v0.7.6` tag pushed while pyproject says `0.7.5` fails the job — the tag==version check lives at release time, not as a pytest that would fail between a bump and its tag), then runs `gh release create --generate-notes --verify-tag`. It is now **idempotent** (`gh release view` → skip), because the automatic path will usually have got there first and a hand-pushed tag for an already-published version should be a quiet no-op, not a red job. `github.ref_name` reaches the shell via `env`, never interpolated into a `run:` step.

Both publishers run on `ubuntu-latest` (no MLX — read a version, call `gh`) with a `contents: write` token and a 10-min timeout, and both declare the **same literal `concurrency` group, `publish-release`**. Groups are repository-wide, which is what makes the two paths mutually exclusive. In `tag-and-release.yml` it sits on the **job**, not the workflow — a workflow-level group is claimed when the *run* starts, before the `if:` is evaluated, so skipped no-op runs would queue in it and could displace a pending manual release; the `concurrency:` block there carries the full reasoning. Guarded by `TestAutoReleaseWorkflow` / `TestReleaseWorkflow`, with `TestWorkflowsAreGuarded` as the reverse guard so a *new* workflow can't land unguarded. A release badge sits in `README.md`, and `pyproject.toml`'s `[project.urls]` `Changelog` points at the Releases page.

**To cut a release:** bump `version` in `pyproject.toml` → `uv lock` → commit → push to `main`. That's all: once CI is green the tag and the release appear.

On the automatic path the tag is created **server-side** by `gh release create --target` rather than by a local push, so a clone stays a fetch behind and `git tag -l` under-reports what shipped. Check `gh release list`, not local tags, before concluding a release was missed: re-dispatching for a version that is already released is a **silent green no-op** (`::notice::`), and the job *fails* only in the other state — tag present, release absent. The tag also anchors to the CI-tested SHA of the **triggering push**, not to the bump commit. Recovery levers if the gate is missed: push anything else to main, `workflow_dispatch` `tag-and-release.yml`, or hand-push the tag (which takes the `release.yml` path). Two states go **silently quiet** — a non-`X.Y.Z` version, and a version whose release already exists — and a `::notice::` in the job log is the only signal. If a tag ruleset on `refs/tags/v*` is ever added, `github-actions[bot]` must be on its bypass list or the publish is rejected at `gh release create` time.

  - `TestThemeConfig` (`.streamlit/config.toml`) · `TestFaviconAsset` (`assets/favicon.png` — plus the `page_icon=` argument that must keep pointing at it) · `TestHooksConfig` (`.claude/settings.json`) · `TestCiWorkflow` (`.github/workflows/ci.yml`).

Those `key_paths`/`spine` lists are a deliberate manual sample, **not** exhaustive: `pad_to_square`, `scale_box`, `normalize_hu`, `tissue_mask` and friends are unguarded, so extend the lists when the doc starts leaning on a new symbol. Only the reverse half — every module under `tests/` is documented — is exhaustive.

Its Features/Setup/Usage prose is unguarded and has to be mirrored by hand.
  - `TestLicense` — the `LICENSE` file ↔ its `pyproject` SPDX declaration ↔ the README License + medical-use Disclaimer sections stay mutually consistent.
  - `TestReadmeAssets` — every repo-relative README link/image resolves (the `docs/screenshot.webp` hero, the sample-data guide, the LICENSE/workflow links), and the README keeps embedding that hero.
- **`tests/test_app_ui.py`** — UI flow via `streamlit.testing.v1.AppTest` (built through `_app_test()`, warmed once by `_warm_streamlit_once`); asserts the per-mode `num_images` reaching the mocked `apply_chat_template` and the token budget reaching the mocked `stream_generate`, the mutual-exclusivity guards, result persistence vs staleness, and CT/WSI error `st.status` states. That made three existing tests vacuous the moment the sidebar landed, and the suite stayed green. One more trap: a `Column`'s own `.columns` **starts with the column itself** (`Block.__iter__` yields `self` first), so the CXR comparison pair is `inputs.columns[1:]`.

## Gotchas

- **AppTest re-execs the script each run** — patch `mlx_vlm.*` (and `openslide.OpenSlide`) at the **source**, not `streamlit_app`; select widgets **by key** (tabs render every widget, so position is ambiguous); chain multiple `.upload()` on one element before a single `.run()`.
- **`AppTest`'s 3s `default_timeout` is a cold-start trap** — a run is ~0.03s warm but 16–20s on the *first* one that renders model output in a freshly synced venv (the first `st.write_stream` pulls in pandas/pyarrow lazily, so the warmup has to click **Run**, not just `.run()`). `_warm_streamlit_once` pays it once under `APP_WARMUP_TIMEOUT` so the per-test `APP_RUN_TIMEOUT` stays tight — the bound is per test, so a generous one multiplies across the file and blows CI's job cap on a hang. Build every AppTest via `_app_test()`: a bare `AppTest.from_file` passes warm and fails cold, and `TestAppTestHarness` pins that no call site reverts. The full arithmetic is in `test_app_ui.py`'s header comment; re-do it before nudging the bound.
- **The success path `st.rerun()`s** — the CT/WSI success-path `st.status` is gone by the time AppTest captures the tree, so assert only the *error* state via `at.status[0].state`.
- **The CT/WSI count slider is RAM-gated, so it may not exist** — below ~22 GiB `ram_aware_slice_cap` returns `(2, 2)` and the tab renders a *caption* ("Limited memory detected") instead of `st.slider`. CI's runner is well under that and always takes the caption branch, so any test touching `at.slider(key="ct_slices"/"wsi_patches")` must call `_force_ram_gib(monkeypatch, 32)` first — otherwise it passes on a 32 GiB Mac and fails in CI. The autouse `_clear_caches` fixture is load-bearing for the same reason: `@st.cache_data` on `_cached_total_ram_gib` outlives an `AppTest` run, so one test's forced RAM would leak into the next.
- **The CT uploader takes no `type=` filter on purpose** (the CXR/WSI ones do) — per-slice DICOMs off a PACS or study CD are routinely **extensionless** (`IM_0001`, a bare SOP UID), so a `type=["dcm"]` "consistency fix" would reject real series (uppercase `.DCM` would survive it — Streamlit lowercases both sides); bad uploads are `load_ct_volume`'s error path instead. A `help=` on the widget says so, since it is the only uploader of the four whose dropzone lists no accepted types. Every other DICOM upload in the suite carries a `.dcm` extension, so `test_ct_accepts_extensionless_dicom_filenames` is the only thing that goes red.
- **`load_wsi_patches` spills the upload with `getvalue()`, not `read()`** — position-independent on purpose, the WSI mirror of `load_ct_volume`'s `seek(0)`: Streamlit keeps the same `BytesIO` in session_state, so a chunked `copyfileobj`/`.read()` refactor (tempting for a multi-GB slide) writes an **empty** temp file on the second Run. Each rewind has its own unit test that re-reads one stream twice — `TestLoadCtVolume.test_rereads_same_streams_after_position_advances` (calls `load_ct_volume` twice on one list) and `TestLoadWsiPatches.test_rereads_the_same_stream_after_position_advances` (advances the stream by hand, then reads back what landed on disk). An `AppTest` can't catch either, since it rebuilds `UploadedFile` from the immutable record each run. This is also why the `@st.cache_data` layer lives in `cached_ct_volume`/`cached_wsi_patches` rather than on the loaders themselves — a decorated loader would serve the second call from cache and both guards would stop testing the rewind (one silently passing, one going red).
- **Never pass `icon=` to an `st.expander` here**, however apt the glyph. `AppTest` classifies an expandable block *by whether it carries an icon* — `element_tree.py`: `if block.expandable.icon: Status(...) else: Expander(...)` — because that is how `st.status` is built. So an icon silently moves the element out of `at.expander` and into `at.status`, where `.state` raises `ValueError("Unknown Status state")` on any glyph that isn't one of `st.status`'s own three (spinner / `:material/check:` / `:material/error:`). Adding `:material/tune:` to "Model settings" and `:material/neurology:` to "Thinking trace" broke five tests at once: the `at.expander` label lookups stopped finding them, *and* the CT/WSI `at.status[0].state` error assertions started reading a settings panel. `type="compact"` is unaffected — it does not touch classification — so the compact style stays. Now pinned by `TestThemeConfig.test_expanders_never_carry_an_icon`, which AST-walks `streamlit_app.py` for `st.expander(...)` calls: that turns a five-test mystery into one named message.
- **`apply_rescale` returns `float64`** — `load_ct_volume` downcasts to `float32`, guarded by `if hu.dtype == np.float64`. The guard is not defensive noise: with a Modality LUT Sequence `(0028,3000)`, or with no rescale tags at all, `apply_rescale` hands back the `uint8`/`uint16` array unchanged, where a blind `.astype(np.float32)` would *double* the footprint instead of halving it. Nothing downstream wants the extra precision — `normalize_hu`'s first move is `.astype(np.float32)`.
- **Streamlit API** — use `width="stretch"`, not deprecated `use_container_width`.

## Constraints

- **No multi-turn chat** — single Q&A per interaction.
- **Package management** — uv (`pyproject.toml` + `uv.lock`); no `requirements.txt`.
- **Python** — pinned **exactly**: `requires-python = "==3.12.*"`, with ruff `target-version = "py312"`. CI has no `setup-python` step, so uv provisions the interpreter from that pin alone — loosening it to `>=3.12` re-locks green while letting CI run a *newer* Python than the local `.venv`. `.python-version` is gitignored, so `uv python pin` produces a pin nobody else sees; pyproject stays the single source, and a change there needs `uv lock`.
- **OpenSlide** — `openslide-python` + `openslide-bin` (native lib ships as an arm64/universal2 wheel; no Homebrew). Single-file WSI formats only; `.mrxs` (multi-file) excluded.
- **HF token** — optional, from `.env` via `python-dotenv`; the MLX repo is ungated, so a token only avoids download rate limits.
- **Theme** — **nord** in `.streamlit/config.toml` (Streamlit's bundled `nord` template, as shipped), locked to a single dark mode by a **lone `[theme]` block**: the light/dark switch appears in the settings menu only when both `[theme.light]` and `[theme.dark]` exist, so re-adding either one restores the toggle. `base = "dark"` seeds everything the palette does not override. The aurora `redColor`/`orangeColor`/`greenColor` are load-bearing — they drive `st.error`/`st.warning` and the CT/WSI `st.status` phase badges. `[theme.sidebar]` styles the app panel `render_sidebar` draws (the nord template's one-step-lighter `#3b4252` surface against the `#2e3440` main area, plus the `showSidebarBorder` rule). nord's stock `font`/`codeFont` (Inter + JetBrains Mono, via a `fonts.googleapis.com` stylesheet) are **deliberately dropped** — inference is on-device, and a webfont would be a per-page-load outbound request; Streamlit's defaults (Source Sans / Source Code, and the Material Symbols face behind every `:material/icon:`) ship in its own static bundle, so unsetting them keeps rendering local. `TestThemeConfig` validates every key against the installed Streamlit *and* fails on any value carrying a URL, so re-pasting the template wholesale goes red. The **favicon** used to be the one hole left: Streamlit resolves a `:material/…:` `page_icon` to an SVG on `fonts.gstatic.com` and refetches it every page load, so the glyph is now vendored to `assets/favicon.png` and passed as `FAVICON_PATH` (served from Streamlit's own `/media/`). It is the Material Symbols Rounded `clinical_notes` glyph (Apache-2.0) **recolored to `#88c0d0`** — the stock glyph is `#000` and all but vanishes against a dark browser tab strip. `TestFaviconAsset` pins the file, its legibility, and that `page_icon` has not drifted back to the remote form.
- **Uploads** — `[server] maxUploadSize = 2000` in `.streamlit/config.toml`. Streamlit's default is 200 MB, which rejects real diagnostic `.svs`/`.ndpi` slides (300 MB – 2 GB) at the **HTTP layer**, before any app code runs and with a generic message — in a tab whose loader and docs both reason about multi-GB slides. `server.maxUploadSize` is the only lever that moves the **server's** limit, which is enforced three times (Content-Length, streamed body, parsed file), each resolving the config option afresh. 2000 and not higher because peak memory is **~2× the file** — the slide sits in `session_state` as a `BytesIO` *and* `load_wsi_patches` copies it whole via `getvalue()` before spilling to a temp file — so a 2 GB slide costs ~4 GB on top of the ~6 GB resident model, on a machine whose slice/patch counts `ram_aware_slice_cap` is already rationing. Raising it further wants a streaming refactor of that spill first; read the `getvalue()`-not-`read()` gotcha before attempting one. Because the ceiling is **global**, the three non-slide uploaders pass `max_upload_size=NON_WSI_MAX_UPLOAD_MB` (200) — most importantly the CT one, which is `accept_multiple_files=True`, carries no `type=` filter by design, and reads every slice fully into memory. Be precise about what that buys, though: `max_upload_size` is a **frontend bound only**. It rides to the browser as `FileUploader.max_upload_size_mb` and *nothing server-side reads it* — every server check resolves `server.maxUploadSize`. So it stops an accidental multi-GB drop on the CT dropzone (the realistic failure on a localhost single-user app) but is **not** a server-enforced cap; a POST bypassing the stock frontend is bounded only by the 2000. `TestThemeConfig` pins the ceiling and the three narrowings as a pair — raising one without the other is the actual regression — and asserts them **per uploader** rather than by occurrence count, so the kwarg cannot drift onto `wsi_files` and still pass.
- **Telemetry** — `[browser] gatherUsageStats = false` in the same `.streamlit/config.toml`. The default is **on**, and Streamlit's frontend then posts to `data.streamlit.io` and a Fivetran webhook on every page load — the largest outbound flow the app would have. Deleting the key is silent (the default takes back over), so `TestThemeConfig` pins it. With it off, the favicon local, and no webfonts, a Playwright request trace of a page load shows **zero off-host requests**; re-run that trace before changing any of the three.
- **Linting** — ruff rule set `E`, `F`, `I`, `UP`, `B`, `SIM`, `C4`; see `[tool.ruff.lint]`.
- **Commits** — Conventional Commits (`feat|fix|docs|test|refactor|perf|style|ci|chore`, optional `(scope)`), lowercase imperative subject with no trailing period, and a body explaining *why*; `main` is linear (no merge commits). There is no hand-maintained changelog — `[project.urls]` `Changelog` points at the Releases page, and since nothing merges via PR here `--generate-notes` emits little beyond a compare link. The commit log **is** the changelog, so write subjects for someone reading `git log`.
